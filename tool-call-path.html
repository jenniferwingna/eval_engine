two-layer-intent branch

从 tool intent 到 tool call

名词解释

编排层
harness 里负责调度所有任务的模块。它自己不做语义判断,只负责「先做这个、再做那个」,并把上一步的结果交给下一步。下面六步里,除了第 3 步(模型判断)和第 6 步(执行端),其余都是它自己干的活。
Head
做一次分类判断的角色,分两级:一级 Head 判「属于哪个大类」,二级 Head 判「大类里的哪个工具」。两级都在同一个模型里 —— 是协议上的两次输出,不是两个独立训练出来的 decoder head,更不是两个模块。本文的起点是一级 Head 已经跑完。

例子

用户说的话: 把空调调到24度

起点:第一跳已经跑完,agenda 当前项的标签是 climate。但还不知道调的是哪个工具、参数是什么。

终点:指令下发出去,拿回一张回执。

架构图

四张图。第一张是工程视角:一共有哪几块、谁跟谁说话、各自负责什么。后三张是数据视角,由远到近:一句话进来会经过什么 → 编排层内部 → 本文这条路。四张画的都是接上模型之后的形状。

二 · 一句话进来，会经过什么、最后变成什么

STEP 1按大类取候选:546 → 18

谁在做  编排层 ·  一行查表,不做判断

第一跳模型已经把整轮话拆成了一张 agenda,当前这一项的标签是 climate。编排层拿这个字符串去查一张进程启动时就建好的表,取出这一类的全部成员。

// streaming/nonrag_agent_backend.py · _current_task_context
intent = task["intent"]              # "climate"
if intent in GROUPS:
    s.active_group = intent          # ← 闭集边界从这一行开始生效
    block = s.catalog.render_group(intent)
输入
intent = "climate"
输出 · 18 个候选
conditioner_switch              空调开/关
conditioner_child_lock_switch   空调儿童锁开/关
conditioner_vent_switch         空调出风口开/关
conditioner_mode                空调的工作模式
conditioner_wind_direction      空调的吹风模式(风向)
conditioner_temperature         调空调温度
conditioner_speed               调空调风量

fragrance_switch                车载香氛开/关
fragrance_density               调车载香氛的浓度
fragrance_type                  调车载香氛的香型或味道
fragrance_random_change         随机切换香氛味道

climate 即「温度与香氛」,里面装着空调 7 个、香氛 4 个、冷暖箱 6 个、杯托 1 个。同一类里有两个「温度」 —— conditioner_temperature 和 fridge_temperature,参数形态还完全一样。下一步要在这两个之间分清楚。

起点那个 climate 是怎么判出来的

一轮对话的第一跳,模型必须同跳、按顺序吐出两条标签,一条都不能少:

§intent climate§
§asr {"transcript":"把空调调到24度","tasks":[
      {"id":"task-1","query":"把空调调到24度","span":[0,8]}]}§

前一条是 Intent Head,给出整轮的有序 agenda;后一条是 ASR Head,给出逐字转写和每个任务的原文切片。多任务时是这样:

用户: 打开空调，播放音乐，然后导航回家

§intent climate,audio,subagent_navigation§
§asr {"transcript":"打开空调，播放音乐，然后导航回家","tasks":[
      {"id":"task-1","query":"打开空调","span":[0,4]},
      {"id":"task-2","query":"播放音乐","span":[5,9]},
      {"id":"task-3","query":"导航回家","span":[12,16]}]}§

标签只能来自一张 22 项的表,由 CATALOG.taxonomy_prompt() 渲染进 system prompt:

  • dialog(1 个)—— 闲聊、问答,不执行任何动作
  • subagent_navigation(1 个)—— 地点、路线、沿途任务,交给导航 Agent
  • 20 个工具大类 —— climate、audio、doors_windows…

这张表一个工具名都没有 —— 第一跳看不见那 546 个工具中的任何一个。

两条标签必须严格对得上，对不上直接拒绝

bind_verified_agenda() 逐项核三件事:数量相同、id 必须是 task-1..N 且顺序一致、非 dialog 的 query 不能为空。任一条不满足就抛错,编排层回一条 _protocol_failure 给模型重来,不会带着半张 agenda 往下走。

安全语义也写在这一跳的 system prompt 里,由模型自己执行,不是编排层的代码:

用户说规则
「别开空调」否定修饰的动作不是待执行任务,不得为它输出工具标签或 call
「如果下雨就关窗」没有事件回执的条件任务归 dialog,说明无法立即执行
「空调开着吗」仍输出 climate,但后续只能用 §state§,绝不能 call

所以没有一个单独的「这是不是控车」的判断步骤,也没有任何打分或阈值 —— 这一跳整个在模型里完成,编排层只做协议校验。

这张 18 个的表是怎么来的

进程启动时读一次工具目录(data/tools_manifest.json,546 个工具),按大类分成 20 个桶:

# streaming/group_catalog.py · ClosedSetCatalog.__init__
self.by_group = {group: [] for group in GROUPS}      # 20 个空桶
for tool in tools:
    if tool.group not in self.by_group:
        raise ValueError(f"manifest contains unknown group: {tool.group}")
    self.by_group[tool.group].append(tool)

每个工具的大类由 classify_tool_group(item) 算出来,算不出来就直接抛错 —— 目录里不允许存在归不了类的工具,闭集这件事在加载时就被强制了。

之后每次请求就只是 self.by_group["climate"],一次查表。没有搜索、没有相关性排序、没有 top-k —— 拿到的是这一类的全部 18 个,一个不多一个不少。

STEP 2压成一行一个工具:18 行 / 970 字符

谁在做  编排层 ·  纯字符串渲染,不做判断

18 个工具对象要变成一段能塞进 prompt 的文本。渲染规则只有一行:

# streaming/group_catalog.py · ToolSchema.prompt_line
params = "；".join(self.raw_params) if self.raw_params else "无参数"
return f"§{self.name} {params}§ — {self.description}"
输入 · 目录里的原始条目
{
  "name": "conditioner_temperature",
  "description": "调空调温度",
  "raw_params": ["set|inc|dec", "Pos?"],
  "category": "空调",       ← 不进这一行
  "group": "climate"        ← 不进这一行，上一步已经确定了
}
输出 · 一行
§conditioner_temperature set|inc|dec；Pos?§ — 调空调温度

Schema 的形状，就是调用的形状

注意这一行两头也是 § §,和模型待会儿要吐的调用长得一模一样。模型要做的只是把参数位换成真值:

看到  §conditioner_temperature set|inc|dec；Pos?§ — 调空调温度
吐出  §call conditioner_temperature set 24§

所以这条路上不需要另外教模型输出格式 —— 格式就长在候选清单里,每一行都是一次示范。

为什么大类必须控制在 40 个工具以内

因为这份清单是整个塞进 prompt 的,而且每切一次 agenda 项就要塞一次。

大类工具数渲染出来
climate18970 字符
mirrors_cameras(现在最大的一类)402773 字符
假设有一类装 141 个141约一万字符

「每类不超过 40 个」是为了让这段注入稳定在三千字符以内。再往上,既拖首字延迟,也让模型在长清单里更容易看错行。

代码里还留了一条泄压阀:注入这段 Schema 时标了 droppable,允许引擎在轮末把它从 KV 里淘汰(执行回执则保留)—— 大类 Schema 是短期工作集,用完就可以扔。

模型这一跳完整收到的文本，一字不差

不只有上面那 970 字符。编排层在每个大类块前面还钉一个任务边界抬头,防止模型跨任务乱答:

【当前 Agenda 任务】
id: task-1
query: "把空调调到24度"
span: [0, 8]
source: logical_asr_head
asr_verified: true
硬约束：只处理上述 task query；不得退回整轮音频猜测其他任务。

【当前任务工具大类：温度与香氛 / climate】
空调、冷暖箱、杯托、香氛和空气环境。只能调用下列静态 Schema；不得创造工具名：
§conditioner_switch on|off；Pos?§ — 空调开/关
…（上面那 18 行）…
§fridge_temperature set|inc|dec§ — 车载冷暖箱的温度

抬头 137 字符 + 大类块 970 字符 = 1109 字符,作为一条 obs 消息直接写进模型的 KV。

query 和 span 都来自上一跳 ASR Head 自己给的切片 —— 模型是在按自己刚才划的边界干活,编排层只是把它固化下来再钉回去。

STEP 3模型一次吐出工具名和参数

谁在做  模型 ·  本文唯一的判断点

上一步那 1109 字符进了 KV,模型接着往下生成。工具名和参数是同一次输出里的同一串文本 —— 不是先选工具再填参数两回事。

输入 · 模型手上有的
当前 task query：「把空调调到24度」
+ 这个大类的全部 18 条 Tool Schema（含参数形态与枚举）
输出 · 模型直接吐出来的
§call conditioner_temperature set 24§
 |    |                       |
 |    |                       +--- 参数     ["set", "24"]
 |    +--- 工具名              conditioner_temperature
 +--- 动作类型（call / state / intent / asr）

system prompt 里对这一跳的全部要求,原文:

系统每次只给你 agenda 当前项所属大类的全部静态 Tool Schema。系统也给出当前
task id/query/span；你必须只回答这个 query，不能从整轮音频猜测、合并或改答其他
task。你只能从当前 Schema 中选择具体工具：
§call 工具名 参数§   执行（如 §call conditioner_temperature set 23 all§）。
参数写法以当前 Schema 为准，枚举值原样照抄。系统执行前会**自动核对该部件当前
状态**，不必先查再调。**同一 task 的多件事可以一跳连发多个 call**。
§state 部件或类目§   只在用户**询问状态**时用（"空调开着吗"→ §state 空调§），
车控操作前不需要它。

这里没有置信度、没有备选、没有排名

模型交出来的是转写流里的一段文本,不是一个 JSON 对象 —— 结构上就没有地方放分数。整条链路上不存在任何一个数字阈值去卡「这次判得够不够准」。

编排层拿到这段文本后能做的判断只有一个:这个工具名在不在当前大类的清单里(见 STEP 5)。判不出「选得对不对」,只判得出「越没越界」。

同一跳可以连发多个 call

一个 task 里如果有多件事,模型可以一次全吐出来,每个动作独立一对 §§,连着写:

§call conditioner_switch on§§call conditioner_temperature set 24§

编排层按顺序逐个执行,把回执按序拼成一条再回灌:

# nonrag_agent_backend.py
elif all(kind == "call" for kind, _ in acts):
    obs_parts = []
    for kind, body in acts:
        o = await _do_action(s, "call", body.strip())
        obs_parts.append(o)
    obs = "\n".join(obs_parts)

但一跳里不能混着来:要么全是 call,要么只有一个 state。混了就回 invalid_followup_actions 协议失败。

另外这是同一个 task 内的多个动作。跨 task(比如「开空调 + 放音乐」)是靠 agenda 串行推进的 —— 第一项的回执成功了才切到第二项,那时候注入的 Schema 已经换成 audio 那一类了。

模型有两种吐调用的通道，殊途同归
通道模型怎么给编排层怎么拿到
DSL 标签
默认		在转写流里直接写 §call 工具名 参数§一条正则扫出标签,按空格切成工具名 + 参数数组
原生 function calling
座舱前端 CFG.fc 打开时		走 response.function_call_arguments.done,给的是一个 JSONJSON.parse 之后按 argmaps[工具名] 排成位置参数

两条最后都汇进同一个 dispatch(name, args, "voice")。无论走哪条,args 里的每一个值都是模型写的。

顺带一个实测细节:FC 模式下音频和对话必须物理隔离成两条连接 —— 同一会话只要 commit 过音频 item,后续函数调用决策就被污染(车控话术被发给 cloud_search,删 item 都救不回);纯文本会话则稳定调对。

STEP 4切出 tool call

谁在做  编排层 ·  一条正则加一次 split,无判断

这一步是「拆」，不是「拼」

模型给的本来就是完整的一条。编排层要做的是把它从口播文本里切出来、再切成工具名和参数 —— 没有任何一个字段是这里生产的。

后端从生成的文本里扫动作标签:

# nonrag_agent_backend.py
ACT_RE = re.compile(r"§?\s*(state|intent|asr|call)\s+([^§]+?)\s*§")

→ kind = "call"
→ body = "conditioner_temperature set 24"

然后一次 split() 就完了:

parts = body.split()          # ["conditioner_temperature", "set", "24"]
name  = parts[0]              # "conditioner_temperature"
args  = parts[1:]             # ["set", "24"]

不带 § 的文本原样留下,就是要播报给用户听的话(DSL_RE.sub("", text))。同一段生成里,动作和口播是靠这对 § 分开的。

tool call

name = "conditioner_temperature"
args = ["set", "24"]
为什么开头那个 § 是可选的 —— 一个 400 条连跑的实测

看正则第一个字符:§?,带问号,可有可无。代码注释里记了原因:

# 开头的 § 是可选的：长会话后模型会漂移成只写收尾 §（实测 400 条连跑到
# 第 ~250 条起，输出全变成 "call xxx dec§" 缺前导 §，整条被当纯文本口播、
# 动作发不出去，150 条全军覆没）。尾 § 仍是必须的，靠它划定动作边界，
# 所以宽容不会把普通口播误吞——口播文本里的 § 早被 DSL_RE 滤掉了。

这条注释顺带说明了一件事:动作能不能发出去,取决于模型有没有把格式写对。缺一个 §,整条就掉进口播文本里,车一动不动。这是「模型直接吐调用」这个设计要付的代价 —— 换成结构化返回就不会有这个问题,但也就拿不到「Schema 形状即调用形状」那份便宜。

座舱前端也自己切一遍

后端切出来是为了执行;座舱页面切出来是为了把仪表盘画对。两边看的是同一段文字流,各切各的:

// public/streaming/omni-app.safe.js
const DSL_RE = /§\s*([^§]*?)\s*§/g;
const { name, args } = V2.parseTag(inside);

前端多做两道琐碎清洗,后端没有:

  • 滤掉照抄的参数占位符 —— 模型有时把 Pos?、color:str?、<param:…> 原样抄进调用里;凡是以 ? 结尾、含 :、或以 < 开头的一律丢掉
  • 把位置词挪到末尾 —— 模型爱写 set all 23.25,而执行端只认 set 紧跟数值,于是重排成 set 23.25 all
STEP 5闭集硬闸 + 参数校正

谁在做  编排层 ·  只拦截和纠正,不生产参数

第一道,也是唯一一道拦在执行前面的:工具名在不在当前大类里。

# nonrag_agent_backend.py · _do_action
allowed = s.catalog.names_for_group(s.active_group)
if name not in allowed:
    return json.dumps({"结果": "失败", …})    # 注意是 return，不是 raise

越界不是抛异常，是回一张「带自救说明的失败回执」

模型吐    §call conditioner_power on§
             ↓  conditioner_power 不在 climate 那 18 个里
硬闸拦下,回一张失败回执:
    { "结果": "失败",
      "原因": "conditioner_power 不属于当前闭集大类 climate",
      "当前大类工具": ["conditioner_switch", "conditioner_mode", …],
      "现在必须做": "只从当前系统给出的 Tool Schema 原样选择并重试。" }
             ↓  这张回执写进模型的 KV
模型再生成一次   §call conditioner_switch on§   ← 这就是一次「重试」

所以「重试」就是多跟模型交互一轮:失败回执进上下文,模型带着它重新生成。回执里直接把当前大类的工具名列给它,不用它自己猜。

「最多 2 次」是写给模型的话，不是代码拦的

system prompt 里那句「失败：按回执给出的当前大类 Schema 改名或改参数重试，最多 2 次」是一条指令,靠模型自己遵守。代码里没有任何计数器去数它重试了几次。

代码里唯一的硬上限是整轮的跳数:

MAX_HOPS = int(os.environ.get("AGENT_MAX_HOPS", "10"))

while hops < MAX_HOPS and not s.cancelled:
    …每回一次模型 hops += 1…

一轮对话里模型总共最多被回到 10 次,重试也算在这 10 次里面 —— 它和「执行成功后继续下一个 task」共用同一个额度。撞到 10 次就跳出循环,把最后那段文本当口播念出去。

触发重试的不只是「选错工具」

任何一张 结果: 失败 的回执都会走同一条路。两个来源:

  • 工具名越界 —— 上面那道硬闸
  • 执行失败 —— 名字对了但参数不合法,car_sim 自己返回失败

两种都不推进 agenda(_obs_succeeded() 为 False),模型停在同一个 task、同一份 Schema 上重来。

第二组,座舱前端对模型给的参数做的四道改写。四道都是在改模型已经填好的值,一道一道看具体在改什么:

#改写前 → 改写后这条规则在干什么
1
模型吐  §call conditioner_power on§
改写成  §call conditioner_switch on§
名字救一把。conditioner_power 这个工具不存在,是模型编的。规则:把名字最后一段换成 _switch 再查一次 —— conditioner_switch 确实存在,而且参数是 on、像个开关,判定模型只是把名字尾巴记错了,改名派发。换完还查不到就丢弃,并在这一轮结束时告诉模型「你编了个工具名」
2
用户说「关上我的车门」
模型吐  §call door_switch off driver§
改写成  §call door_switch off secondRowLeft§
位置重算。「我的」指的是说话人坐哪儿,麦克风阵列的音区知道 —— 比如人坐在二排左。模型填的 driver 是猜的。规则查一张座位表算出真实位置,无条件覆盖模型填的那个位置词(模型碰巧填对时覆盖成同值,没副作用)
3

4

改写成  §call fridge_mode on 制冷§
中英归一。目录里这个工具的枚举写的是「制冷」,模型爱吐英文。查一张小映射表(auto→自动、dark→深色、cool→制冷…)换过来。换完还要确认换出来的词确实在这个工具的枚举里才替换 —— 否则 on/off/set 这些协议词会被误翻

这四道是纯规则,模型完全不参与

四道全是座舱前端 JS 里的确定性代码:if / 正则 / 查表,没有一次模型调用,也不消耗任何 hop。 它们跑在前端把 §call§ 切出来之后、往仪表盘上画之前那一瞬间,入口只有一个 —— dispatch(name, args, 'voice')。

而且它们只在 source === 'voice' 时才跑:手动点按钮、系统联动(上车唤醒/泊车熄火)都绕开这一段,因为那些参数不是模型给的。

「查一张座位表算出真实位置」到底怎么算

两步:先知道说话人坐哪儿,再查表。没有几何计算,也没有推理。

第一步,说话人坐哪儿 —— 页面上就是个下拉框 #seatSelect(真车上这一格由麦克风阵列的音区判定填)。它给出一个座位枚举,比如 secondRowLeft。

第二步,查表 —— 一个座位一行,每行写死了「这边/左边/右边/前面/后面」各自等于哪个具体位置:

// public/streaming/omni-app.safe.js:501  映射表现算好直接给
//（抽象换算规则小模型走不稳，具体表照抄就行）
const SEAT_REL = {
  driver:         { 这边:'driver',        左边:'driver',        右边:'copilot',        后面:'secondRowLeft' },
  copilot:        { 这边:'copilot',       左边:'driver',        右边:'copilot',        后面:'secondRowRight' },
  secondRowLeft:  { 这边:'secondRowLeft', 左边:'secondRowLeft', 右边:'secondRowRight', 前面:'driver',  后面:'thirdRowLeft' },
  secondRowRight: { 这边:'secondRowRight',左边:'secondRowLeft', 右边:'secondRowRight', 前面:'copilot', 后面:'thirdRowRight' },
  // …thirdRowLeft / thirdRowRight 同理
};

怎么知道用户说的是哪一格 —— resolveRelativePos() 拿本轮原话按顺序试几条正则,命中哪条就取表里对应的那一格:

原话里出现取表里的坐在 secondRowLeft 时结果
我左边 / 我左侧 / 我左手左边secondRowLeft
我右边 / 我右侧 / 我右手右边secondRowRight
我前面 / 我前方前面driver
我后面 / 我后方后面thirdRowLeft
我这边 / 我旁边 / 我身边这边secondRowLeft
我的车门 / 关我车窗(只有所有格,没方位)这边secondRowLeft

先剥助词式的「我」。「帮我 / 给我 / 让我 / 我想 / 我要」里的「我」不是位置语义,剥掉之后句子里还剩「我」才继续往下算 —— 否则「帮我开空调」会被当成「开我这边的空调」。剥完不剩「我」就直接 return null,这一道整个不动。

算出来之后怎么用 —— 在 args 里找第一个长得像位置的参数(driver|copilot|secondRow…|left|right|all…),找到就原地换掉,一个都没有就追加到末尾。这是无条件的:模型填对了也覆盖一遍,填成同值,没副作用。

不带「我」的说法不走这条路

「右边的车窗」这种没有「我」的区域说法,直接用聚合枚举 right,不换算 —— resolveRelativePos() 第一行 if (!text.includes('我')) return null 就挡住了。只有「我 + 方位」才是相对的,才需要知道说话人坐哪儿。

这四道的存在本身就是证据

它们全部是在修模型填出来的东西:覆盖模型填的位置、模型吐空参时才补、模型吐英文枚举时映射成中文、模型编工具名时救一把。

如果参数是编排层自己从原话抠的,这些逻辑一条都不需要存在。

三个词分清楚：覆盖 / 兜底 / 归一

它们经常被一起说成「规则兜底」,但触发条件完全不同,遇到 bug 时找错地方会绕很久:

什么时候动模型给对了会怎样
覆盖 第 2 道原话里有「我的/我这边」就动,无条件算出同值,覆盖成一样的,无副作用
兜底 第 3 道只在一个真参数都没有时才动一个字都不改,直接返回
归一 第 4 道每次都跑,但只在映射结果落在该工具枚举里才替换已经是中文枚举,映射表里查不到,原样返回

只有第 3 道是真正意义上的「兜底」。另外两道在模型给对的时候也照跑。

结果 只有三种:

模型下一跳是带着这张回执继续生成的。所以它说的那句「已经调到24度了」,依据是回执里的「现态: 24℃」,不是它自己以为发出去的那条调用。回执被钳到 32 度,它就得说 32。

推进 agenda 是什么意思

回想 STEP 1:第一跳模型已经把整轮话拆成了一张有序任务清单。比如「打开空调，播放音乐，然后导航回家」拆成:

task-1  climate               ← 指针在这儿
task-2  audio
task-3  subagent_navigation

「推进 agenda」就是把这个指针往下挪一格。挪的时候顺带做两件事:把 active_group 换成下一项的大类,把那一类的 Schema 重新渲染一遍注入进去 —— 于是模型手上的候选清单从 climate 那 18 条换成了 audio 那一类。

成功才挪:

if _obs_succeeded(obs_parts):
    next_context = await _advance_agenda(s)

失败就停在原地,注入的还是同一份 Schema,模型对着同一个 task 重来。这就是「一个任务没做成,不会带着它往下走」。

演示路判断:离线打分器

谁在做  离线打分器 ·  只存在于 src/classifier.js

给 18 个候选各打一个分,最高分胜出,再按「第一名领先第二名多少」折算出一个置信度。这个数不参与任何判断 —— 全流程没有一处拿它做阈值拦截,算出来只在界面上显示成一个百分比。前三名:

名次工具描述得分
1conditioner_temperature调空调温度26
2conditioner_speed调空调风量14
3fridge_temperature车载冷暖箱的温度12
0.92 这个置信度是怎么算的，以及它到底有没有用

计算「第一名领先第二名多少」：

公式
confidence = 0.52 + (第一名得分 − 第二名得分) ÷ (第一名得分 + 4)
代入本例
= 0.52 + (26 − 14) ÷ (26 + 4) = 0.52 + 0.40 = 0.92

为什么分母是「第一名得分 + 4」:

  • 先说除以第一名得分 —— 把「领先了几分」换算成「领先了多大比例」。26 比 14 领先 12 分,和 260 比 140 领先 120 分,应该给出同一个置信度;除一下就把分数的绝对大小抹平了。
  • 再说那个 +4 —— 防止分母太小,把低分票捧上天。如果只除以第一名得分,一个 1 分对 0 分的候选会算出 0.52 + 1/1 = 1.52(截到 0.99),可它其实只命中了一个很轻的线索。加了 4 之后,同样这一票只有 0.52 + 1/5 = 0.72。分数越低,4 在分母里占比越大,压得越狠;分数一旦上去(26 → 30),4 就几乎不起作用。所以 4 是一个「低分打折」的档位,数值本身是拍出来的常数,没有推导过程。

三个边界:

情形算出来含义
第一名和第二名打平0.52下限。领先幅度为 0,分式那一项就是 0。不给 0 分 —— 闭集里必须选一个,选出来的不是「毫无依据」,只是没拉开差距;下限定在 0.5 往上一点,是为了和下面那个 0.2 明显分开
第一名遥遥领先0.99上限,被 Math.min(0.99, …) 截住。不给 1.0 —— 留一格表示「再干脆也不等于确定」
所有候选都是 0 分0.2特判。一条线索都没命中,此时排第一的只是工具名字母序最靠前的那个,分数本身没有意义,所以直接给一个明显偏低的数

所以这个数字描述的是第一名比第二名高出多少,和「答案对不对」没有关系。0.92 的意思是「26 分把第二名的 14 分拉开了 12 分」,不是「有 92% 的把握选对了」。

而且它不参与任何判断 —— 全流程没有一处拿它做阈值拦截,算出来之后只在界面上显示成一个百分比。

打分公式拆开看，26 分是怎么来的

每个候选的分数是六项加减:

score = exactScore          // 工具的分类名/描述/可选值，整串出现在原话里 ×2
      + nameScore           // 英文工具名拆词 → 查中文别名表，别名在原话里 ×5
      + phraseScore         // 分类名+描述切成 2~6 字片段，命中一个加它的字数
      + actionBonus         // 原话「打开/关闭」对上描述里的「开关」，+2
      + semanticBonus       // 温度 / N度 ↔ 名字含 temperature，+12（压倒性）
      - specificityPenalty; // 工具名下划线超过 2 段，每多一段 −1.5

逐项看一遍。括号里是 conditioner_temperature 在「把空调调到24度」这句上的实得分:

exactScore ×2 (+2)
拿工具的分类名、描述、可选值去原话里找整串。分类名「空调」在原话里 → +2;描述「调空调温度」整串不在原话里 → 0;可选值 set/inc/dec 是英文,中文句子里不会出现 → 0。
nameScore ×5 (+5)
把英文工具名按下划线拆开,每一段去查一张手写的中英别名表(conditioner→空调、temperature→温度、seat→座椅/座位、switch→开关/打开/关闭… 共二十来条)。别名出现在原话里就 +5。本例 conditioner→「空调」命中 → +5;temperature→「温度」没命中 —— 用户说的是「24度」,不是「温度」→ 0。
phraseScore 权重=片段字数 (+7)
把分类名和描述连成一串,切出其中所有 2~6 字的连续片段,哪个片段出现在原话里就加它的字数。本例这串是「空调」+「调空调温度」= 空调调空调温度,在原话里命中三个片段:「空调」+2、「调调」+2、「空调调」+3 → 共 +7。片段越长说明重合越多,给分越高;「打开/关闭/设置/模式/功能/控制」这类太通用的片段被一张黑名单排除,不计分。
actionBonus +2 (0)
原话里有「打开/开启」并且工具描述里有「开关」字样 → +2;「关闭/关掉」同理。这条是专门喂给 xxx_switch 那类开关工具的。本例原话是「调到」,不命中。
semanticBonus +12 (+12)
全表只有两条,但权重压倒性:原话出现「温度」或「N度 / 冷一点 / 热一点」且工具名含 temperature → +12;原话出现「风量 / 风速 / N档」且工具名含 speed → +12。本例「24度」命中第一条 → +12。这一项就是为了把「调温度」和「调风量」掰开才加的 —— 这两件事中文里都说「调空调」,靠前面几项分不出来。
specificityPenalty −1.5/段 (0)
工具名下划线段数超过 2,每多一段扣 1.5。conditioner_temperature 是 2 段,不扣;conditioner_child_lock_switch 是 5 段,扣 4.5。含义是名字越长的工具越具体、越冷门,没有明确线索时不该被选中。
合计
2 + 5 + 7 + 0 + 12 − 0 = 26

另外两名:

  • conditioner_speed(14)—— 前三项和第一名一模一样(2+5+7=14),因为它的分类名同样是「空调」;只是原话里没有「风量/档」,拿不到那 +12。
  • fridge_temperature(12)—— 只拿到那 +12。它的分类名是「冷暖箱」、描述是「车载冷暖箱的温度」,和原话里的「空调」完全不重合,前三项全是 0。

同分时按工具名字母序决定名次 —— 这也是演示路会选错工具的一个直接来源。

演示路参数:六条正则

谁在做  编排层 ·  判别方不参与

演示路上判别方的返回格式只有 {tool, confidence, rationale},没有 parameters 这个键,所以参数改由编排层用六条正则从原话里抠一个出来顶替。

输入

choices = ["set", "inc", "dec"]     ← 这个工具认的可选值
输出
parameters = [ "set", "24度" ]
Demo 里模型确实交不出参数 —— 两处代码

① 判别方的返回契约里没有 parameters:

// src/classifier.js · OpenAICompatibleClassifier.selectTool
system: "…提取参数时只能使用 schema 给出的枚举或用户明确给出的数值。
        返回 JSON: {tool, confidence, rationale}"     ← 没有 parameters

return { tool, confidence, alternatives, rationale };    ← 也不透传

这段 prompt 自己是矛盾的:前半句要求模型提取参数,后半句给的返回格式里根本没有 parameters 这个键。那半句在这条演示路上是一条死指令。

② 于是编排层无条件用正则顶上:

task.text 是切分后的用户原话。这一行只从 selection 里取走了 tool 一个字段。

六条规则从上到下依次全部执行

每一条都会跑,命中就往结果列表里加,所以一句话可以同时命中好几条。

六条规则在本例中的实际命中情况:

#规则在找什么本例结果
1可选值字面命中原话里有没有直接出现 set/inc/dec没有 —— 中文句子里当然不会有英文单词
2媒体动词映射播放→play、暂停→pause、继续、下一首、上一首不适用 —— 这个工具没有这些可选值
3on/off 兜底
(仅当第 1 条没命中时才跑)		「打开/开启/启动」→ on,「关闭/关掉/停止」→ off不适用 —— 这个工具没有 on/off
4数字正则抓第一个数字;若工具认 set,把 set 插到最前抓到「24度」 → 插入 set,再追加 "24度"
5增减「调高/升高/大一点」→ inc,「调低/降低/小一点」→ dec没有 —— 用户说的是具体数值,不是增减
6位置词主驾/副驾/前排/后排/左后/右后/全车/全部没有 —— 用户没说位置

所以本例只有第 4 条起了作用,产出 ["set", "24度"]。

「调到」这个动作之所以变成 set,是由「句子里有数字」这一条推出来的 —— 不是靠理解「调到」这两个字。如果用户说「把空调设成24度」,走的是完全一样的路径;但如果说「把空调调高一点」,第 4 条不触发(没数字),改由第 5 条产出 inc。

看六条规则的实际代码
const values = [...tool.primaryChoices, ...tool.secondaryChoices];
const mentioned = values.filter((value) => query.includes(value));
const parameters = [];

// ① 可选值字面命中
if (mentioned.length) parameters.push(...mentioned);

// ② 媒体动词映射
if (/播放/.test(query) && values.includes("play")) parameters.unshift("play");
if (/暂停/.test(query) && values.includes("pause")) parameters.unshift("pause");
if (/继续/.test(query) && values.includes("resume")) parameters.unshift("resume");
if (/下一首|下一个/.test(query) && values.includes("next")) parameters.unshift("next");
if (/上一首|上一个/.test(query) && values.includes("previous")) parameters.unshift("previous");

// ③ on/off 兜底 —— 注意条件里的 !mentioned.length，这就是对①的依赖
if (!mentioned.length && /打开|开启|启动|播放/.test(query) && values.includes("on")) {
  parameters.push("on");
}
if (!mentioned.length && /关闭|关掉|停止|暂停/.test(query) && values.includes("off")) {
  parameters.push("off");
}

// ④ 数字 —— 本例唯一命中的一条
const number = query.match(/-?\d+(?:\.\d+)?(?:%|度|档)?/);
if (number && values.includes("set") && !parameters.includes("set")) parameters.unshift("set");
if (number && !parameters.includes(number[0])) parameters.push(number[0]);

// ⑤ 增减
if (/调高|升高|增加|高一点|大一点/.test(query) && values.includes("inc") && !parameters.includes("inc")) {
  parameters.unshift("inc");
}
if (/调低|降低|减少|低一点|小一点/.test(query) && values.includes("dec") && !parameters.includes("dec")) {
  parameters.unshift("dec");
}

// ⑥ 位置词
const zones = query.match(/主驾|副驾|前排|后排|左后|右后|全车|全部/g) || [];
for (const zone of zones) {
  if (!parameters.includes(zone)) parameters.push(zone);
}

return parameters;

unshift(插到最前)和 push(追加到最后)的区别是刻意的:动作类插前面,数值和位置跟后面,让结果读起来是「设定、24度、主驾」这种顺序。每条都带 !parameters.includes(...) 去重,同一个值不会被加两次。

演示路执行端:一张内存表

谁在做  执行端 ·  逻辑 Demo 里是一个模拟器

tool call 成型之后要交出去执行。这一步的形态可能和你预期的不一样。

输入
tool       = 那个工具对象本身（不是名字字符串）
parameters = ["set", "24度"]
输出 · 回执
{
  "ok": true,
  "tool": "conditioner_temperature",
  "description": "调空调温度",
  "previous": null,                   ← 这个工具改动前的值
  "current": ["set", "24度"],         ← 改动后的值
  "receipt": "调空调温度：set、24度"   ← 拼给播报用的人话
}

「下发」在这里就是一次进程内的函数调用

没有序列化、没有网络、没有请求 ID、没有超时、没有重试、没有鉴权。编排层把整个工具对象连同参数数组直接当函数参数传进去,同步拿到返回值。

所以严格说,这里不存在一个「下发出去的报文」 —— 上面那个 {tool, parameters} 的 JSON 是为了讲清楚才画出来的形状,代码里它从来没有被序列化成文本过。

这一步实际做的事只有三件:

#做什么细节
1空参数兜底parameters.length ? parameters : ["trigger"] —— 参数是空数组时,替换成 ["trigger"]
2写状态往一张以工具名为 key 的内存表里写一笔。一个工具一个槽位,新值直接覆盖旧值,旧值作为 previous 一起返回
3拼回执`${工具描述}：${参数.join("、")}` —— 纯字符串拼接

拼回执之前没有任何成功判断

回执里那个 ok: true 是写死的字面量 —— execute() 里没有失败分支,而且全仓搜下来,这个 ok 只有写入的那一处,没有任何地方去读它。

所以第 3 条那句拼接是无条件执行的:参数是什么就播报什么。它描述的是「我们下发了什么」,不是「车上执行成功了」。逻辑 Demo 里执行端是一张内存表,本来也没有会失败的地方;真接到车上时,这里正是需要补一个真实执行结果回填的位置。
