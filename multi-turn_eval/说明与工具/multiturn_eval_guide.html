§1

先搞清楚它在测什么

每条用例只盯一件"助手在多轮对话里容易栽的跟头"——不是"这句话答得好不好"，而是"这个坑它有没有踩"。17个维度按坑的类型分成5组。每张卡片里的"反例"是最该先看的东西：那就是这条维度存在的理由。

§2

拆开一条用例：三层结构

不管属于哪个维度，每条用例的字段都分三层：剧本层写这场对话怎么发生，判分层写检查轮次该看什么、怎么判对错，溯源层记这条用例从哪来、有没有人复核过。下面用真实的一条 P0 用例（CLARIFY-001）走一遍。

核心原则：剧本写"目标 + 条件"，不写台词。

轮次脚本里绝不会出现"用户说：请把车窗打开一条缝"这种写死的句子，只会写"目标：结合两名后排儿童都怕闷的背景提出把一扇车窗开条缝；条件：不提供左右或具体排位"。这样跑用例的模拟用户（或人）才会根据助手实际的反应调整说法，而不是不管助手说了什么都照稿子念下一句——那样会把本来答对的助手判成答错。

§3

为什么脚本写"目标"，不写"台词"

这份用例不是给测试员照着念的对话稿，是给一个扮演用户的 LLM 模拟器用的驱动脚本——模拟器每一轮先读座舱 agent 刚才实际说了什么，再按"目标 + 条件"现场生成这一轮该说的话，而不是照抄一句写死的台词。这不是随手为之的写法，是为了解决固定台词脚本在多轮测试里一个具体、会直接产生假阴性的问题。

固定台词会怎么坏：

假设 CLARIFY-001 第3轮的台词写死成"好的，那就右后车窗开条缝"。如果检查轮（第2轮）助手实际反应和预想的不完全一样——问法不同、多确认了一句、或者没有恰好按预期只问"哪一扇"——固定台词照样往下念，看起来对话接得上，但已经悄悄把"检查轮该不该问"这个考点本身污染了：要么该给的信息在错的时机被喂了进去，要么台词答非所问。结果是本该判对的 agent 被脚本自己的错位问倒，或者本该判错的 agent 被脚本意外喂对了答案——两种情况评出来的分数都不代表 agent 的真实能力，这就是"把 agent 判死"的意思。

让模拟器"现场生成"而不是"照读台词"，本质上是把"这一轮该出现什么信息、不该出现什么信息"这个约束，从写死在一句具体的话里，改成写进生成规则里——同一条规则能适配 agent 给出的任何合理反应，而信息边界（比如"首轮不能推出 position"）仍然被条件严格锁住，不会因为要适配 agent 的反应而被放松。

对比
固定台词
一句话写死。agent 实际反应对不上台词时，对话要么失真，要么意外泄露/遗漏本该受控的信息
✕
这份用例
目标 + 条件
模拟器读 agent 真实反应后现场生成这一轮，条件作为硬约束锁住考点，措辞可以自由变化

这也是为什么同一条用例要靠"轮次变体"重跑很多次，而不是只写一版剧本——单跑一次，分不清"agent 答对了"还是"这次模拟器凑巧问得简单"。文档里把这种全程实时生成的跑法叫"模拟器闭环"，标注"贵，但才是真实形态"；还有一种更便宜的"静态回放"——前面几轮固定，只让模型生成最后一轮——它自己写明了"测不出误差累积，分数不能拿来解释真实链路"，只适合日常冒烟测，版本准入门槛必须用闭环模式。这是一个显式的成本/真实度权衡，不是把便宜方案包装成完整方案。

§4

六种判分手段，从上到下越来越贵

"判分载体"这个字段就是在指定用哪一种（或哪几种叠加）。能用便宜的程序化判分就不用贵的人工判分——判分方式一旦定错，这条用例后面全部白做。

代号手段怎么判谁来判成本
成本从①到⑥递增，原因不是"都要人工"，是判定这一步谁来做：

①②③是代码直接比对状态/调用记录，成本最低；④也是代码比对，但要先从自然语言回复里抽取结构化事实，抽取规则本身要单独测，成本中等；⑤不是人，是把检查轮次的内容丢给一个判分用的 LLM 回答一个专属 yes/no 问题，成本中等，但一致性依赖判分模型能力和问题写得够不够窄；只有⑥是真的人工——按比例抽样人读，成本最高，全数据集里只有"自我一致"这一个维度用到它。

⑤二元问题有硬约束，缺一不可：

必须窄化成 yes/no、必须是这条用例专属的问题（不能是"回复自然流畅吗"这种通用问法）、必须只看检查轮次的内容。这三条不满足，不同判分员/判分模型给出的结论一致率会从九成掉到四成以下——等于这条用例的分数没意义。

需要人工的评测方法是不是"不好"？

不是天然不好，是对"验证本身跟做题一样难"的判断如实承认——比如"被质疑后立场是否还和第1轮一致"，没有一条程序化规则能可靠替代人读。硬把它塞进一个自动规则，会得到一个看起来严谨、实际不代表真实能力的假分数，比承认"这里需要人"更糟。让这个方法"好"的是三个约束：只在自动化真的做不到的地方用（这里是17个维度里的1个）、按比例抽样而不是每次重跑都要人判、并且有"两人独立判是否一致"这道校准检查兜底——一旦这三条松动，人工抽检就会从"必要的兜底"退化成"没人认真做判分设计的借口"。

§5

一条用例怎么跑、怎么出结果

用例本身是"剧本+判分标准"，不是可执行代码。跑起来需要一个执行方——一个扮演用户的 LLM 模拟器全程实时对话，照剧本逐轮驱动座舱 agent，到检查轮次按判分层的标准打分，再按轮次变体重跑 n 次。

通过 = 判分输出 == 期望答案，不是恒等于"yes"

"期望答案"字段有时是 no（比如虚假记忆诱导，期望助手识破而不是照办）。单次是否"通过"，看的是判分手段实际给出的结论和期望答案是否一致；如果判分载体叠加了多种手段（比如③禁止动作+⑤二元问题），是"两者都通过"才算这次通过——③是一票否决，不是拿来平均的分项。

n 怎么定：不是固定值，看这条用例的分量

n 是设计时定的自变量，不是跑出来的结果——最容易犯的错是拿 n=5 的数据硬报"10 分位"（5 次里的10分位就是最差那一次，单次极值本身很不稳）。

重跑 n 次之后，看的是分布形状，不是平均分

同一条用例10次里有6次过，"60%"这个数字本身没告诉你该往哪修。10次的通过/失败排成一排，形状不同，说明的问题完全不同：

三种跑法，只有一种能撑起上面这套分布读法

§6

850条怎么汇总成一个能拍板的结论

单条用例的通过率要一层层卷上去，才是"能不能上车"的结论。中间有两处最容易被抹平、看漏：

卷1
用例 → 维度
50条用例的通过率取均值，得到这个维度（如"该问/不该问"）的通过率
→
卷2
维度 → 分组
按5个分组（记忆与约束/一致性与版本/交互决策/任务连续性/异常与状态）汇总，定位是哪一类能力薄弱
→
卷3
P0 是否清零
6个P0维度（300条）是发布前必须过的门槛，P1/P2是补充信号，不能拿P1的高分去掩盖P0的坑
正例/负例必须分开报，不能合并成一个数字。

比如"该问/不该问"维度50条里正例、负例各25条：正例测的是"该问的时候真的问了"，负例测的是"不该问的时候没有多此一问"。如果合并只报"这个维度70%通过"，完全可能是负例100%通过、正例只有40%通过——助手其实是"该问的时候也不问"，只是恰好在负例里蒙对了。分开报才能看出这是哪种缺陷。同理，虚假记忆诱导维度负例占比100%（50条全是"用户编造历史，助手该不该识破"），这类维度的负例比例本身就是设计的一部分，不是数据缺陷。

§7

入库前 7 项自检

一条用例写完、判分方式定完之后，入库前逐条过一遍这7项——大部分返工都是因为漏了其中一两项。

§8

有850条用例、一个 Harness 工程、一个模型——离主管要的指标还差什么

用例本身只是"剧本+判分标准"，是数据，不是可执行的评测系统。从这份数据跑出一个能给主管看的指标，中间还要建这几层：

环节现在有什么还缺什么
用户模拟器用例里的目标+条件规则、用户画像一个能读"agent 真实上一轮回复"+目标+条件，现场生成这一轮用户话术的 LLM 服务；上线前要先对参考 agent 跑一遍、按第7项自检标定"用户侧错误率"
Harness 执行编排Harness 工程骨架解析这份 JSON（17个维度字段形状不完全一致）→按轮次脚本逐轮驱动→灌初始状态→区分"这轮是用户还是助手"的适配层——这一层要先确认 Harness 工程现在到底能不能跟 SUT 来回对话，还是只是骨架
日志埋点—每轮完整落盘：助手回复文本、工具调用名+参数、状态增量、时间戳，结构化 trace，不是打印在控制台
判分引擎每条用例已标注该用哪种判分载体①②③④的代码比对器（要按维度归一化字段形状）；⑤的判分模型 prompt 模板+两人一致率校准；⑥的人工抽检队列/界面
重跑与变体轮次变体规则、重跑 n真正按 n 和变体规则跑 n 次、每次独立记录结果的执行循环，不是跑一次当结果
统计汇总—单例通过率、分布形状判定（双峰/长尾等）、用例→维度→分组→P0门槛三层卷积，正负例分开算，不能合并
判定基准—和主管对齐"多少算过"：每个 P0 维度/整体的通过率门槛，或者拿哪个版本/基线做对比——没有这条，"70%"这种数字没法得出"好还是不好"的结论
数据可信度自检状态目前多数还是"待独立复核"至少 P0 那 300 条要走完入库前7项自检（我们已经核过一轮、修了1处），指标才立得住
成本预算—850条×n次×判分模型调用的时间/费用估算，尤其如果每个模型版本迭代都要重跑一遍
不建议一次把17个维度全打通再出第一份指标。

300条P0（6个维度）本来就是发布门槛，判分手段也相对集中（主要是①③④⑤，只有自我一致用到⑥），而且已经过完一轮内容审查。先把这300条的完整链路跑通、出第一版P0指标，比同时铺开17个维度、什么都做一半更快让主管看到东西，也更容易在做的过程中发现Harness工程里哪一层缺得最狠。

§9

怎么跟别人讲这份评测集

如果只有三十秒，按这个顺序讲：

简报要点

  1. 这不是850道问答题，是850段写死了"在第几轮检查、期望发生什么、绝对不能发生什么"的多轮剧本，每条只盯车控助手在对话里容易踩的一种坑。
  2. 17种坑分5类：记不记得住早先说过的话、改口后一不一致、该问的时候问不问、被打断后接不接得回去、状态错了知不知道。
  3. 判分方式写在每条用例里，不是临场发挥：能程序化判的（终态/轨迹/禁止动作/结构化信息）就不用人；实在没法程序化的才用一个专属的yes/no问题交给判分模型，再不行才上人工抽检。
  4. 因为模型会抖动，每条用例都按变体规则重跑多次，报的是通过率和失败分布形状，不是单次对错。
  5. 300条P0（6个维度）是能不能上车的硬门槛，正例负例分开看，别用一个平均分把问题盖住。
