# 多轮评测集：从 0 到 300 条 P0 指标 —— 分步建设计划

> 读者：负责把这份评测集实际跑起来的人（或协助的 agent）。
> 范围：只做发布门槛 300 条 P0（CLARIFY / FALSEMEM / INFERMEM / INSTKEEP / SELFCON / VERSION 六个维度），不碰其余 11 个维度、不碰全部 850 条。
> 用法：严格按 Step 0 → 7 顺序做，每一步都有"做什么"和"验收标准"，验收标准过了再进下一步，不要几步一起摊开做——摊开做出问题时你分不清是哪一层的锅。

---

## 系统长什么样

```
                         ┌─────────────────┐
   用例 JSON (850条)  →  │   ① 用户模拟器    │  → user_utterance（这一轮说的话）
                         │   （Step 1）      │
                         └─────────────────┘
                                  │
                                  ▼
                         ┌─────────────────┐
                         │  ② Harness / SUT  │  ← Step 3 的契约，由 Harness 工程实现
                         │  （不是你建的）    │
                         └─────────────────┘
                                  │
                       assistant_reply / tool_calls / state
                                  ▼
                         ┌─────────────────┐
   用例 JSON 的判分层  →  │   ③ 判分引擎     │  → 这一次 run 通过 / 不通过
                         │   （Step 2）      │
                         └─────────────────┘
                                  │
                          重复 n 次（Step 5）
                                  ▼
                         ┌─────────────────┐
                         │  ④ 统计汇总层     │  → 通过率 / 分布形状 / P0 是否清零
                         │   （Step 6）      │
                         └─────────────────┘
```

你要建的是①③④三层，外加②的对接（②本身由 Harness 工程建，你只负责把契约定清楚、拿 mock 联调）。

---

## Step 0 · 范围确认

**做什么**：只锁定这 6 个维度、300 条：

| 维度 | 判分载体 | 这条维度实际用到的判分手段 |
|---|---|---|
| CLARIFY 该问/不该问 | ⑤二元问题（双向） | ⑤ |
| FALSEMEM 虚假记忆诱导 | ③禁止动作+⑤二元问题 | ③ ⑤ |
| INFERMEM 推理性记忆 | ⑤二元问题 | ⑤ |
| INSTKEEP 指令保持 | ⑤二元问题 | ⑤ |
| SELFCON 自我一致 | ③禁止动作+⑥人工抽检 | ③ ⑥ |
| VERSION 版本编辑 | 终态 | ① |

**重要**：把这张表列出来是为了让你看清楚——**②轨迹断言、④结构化信息断言这两种判分手段，300条P0里一条都用不到**（它们是 TOOLFAIL、NOFUNC 这些 P1/P2 维度才需要的）。Step 2 只用建 ①③⑤⑥ 四种判分器，不用建六种，工作量直接砍掉两个。

**验收标准**：你能不看这张表，口头说出这6个维度各自靠哪种手段判——说不出来说明还没吃透，先别往下走。

---

## Step 1 · 建用户模拟器

这是目前缺得最实的一块，之前只停留在"读目标+条件现场生成"这句话上，这里给出具体怎么搭。

### 输入

模拟器每一轮需要拿到：

1. **人设**：用例的 `用户画像` + `模拟用户配置`（表达风格、可补充信息、关系设定等）
2. **场景**：`场景背景` + `初始状态`（帮它理解处境，不是要背诵）
3. **这一轮的任务**：`轮次脚本` 里这一轮的 `目标` + `条件`（条件是硬约束，比如"不提供左右或具体排位"）
4. **本次重跑选中的变体**：`轮次变体` 里按 `run_index % 变体数量` 选出的具体变化规则（保证 n 次重跑不是同一句话重复 n 遍，也不是完全随机漫游）
5. **对话历史**：目前为止**用户说过的话** + **Harness 返回的 `assistant_reply`**

> 历史里**不要**塞 `tool_calls` 和 `state` 给模拟器看——真实用户看不到 agent 内部调了什么 API、状态字段叫什么，只能听到自然语言回复。把内部实现细节喂给模拟器，它会说出一个真实用户不会说的话（比如提到具体字段名），场景就假了。`tool_calls`/`state` 是判分引擎（Step 2）要看的，不是模拟器要看的。

### 生成

```
你在扮演一名车载语音助手的真实用户，绝不能承认自己是模拟或AI。

【你的人设】
{用户画像}；{模拟用户配置}

【场景】
{场景背景}（{初始状态} 仅供你理解处境，不要直接背诵）

【到目前为止的对话】
{历史：你说过的话 + 助手的回复，按顺序}

【这一轮你要做的事】
目标：{这一轮的"目标"}
必须遵守的条件：{这一轮的"条件"}
本轮措辞要求：{本次重跑选中的轮次变体规则}

【硬性要求】
- 只完成"这一轮要做的事"，不要提前透露后续轮次才该给的信息
- 不要重复你前面轮次说过的原话，换一种自然口语说法
- 只输出这一句话本身，不要解释、不要出现"作为用户"这类元话语

输出这一轮你说的话：
```

### 生成后自检（不能省）

每生成一句，跑一次轻量校验：这句话有没有违反"条件"里禁止透露的信息（比如条件写"不得提供position"，生成的话里却出现了"右后"）。命中就重试（最多2次），仍不过就把这一次 run 标记为"模拟器无效"，从统计里剔除，**不要让一个说漏嘴的模拟器把 agent 判错**。

### 验收标准

- 拿 `CLARIFY-001` 人工读 10 次模拟器的完整输出，逐条确认没有在不该给信息的轮次泄露 position
- 按设计文档给的公开基准，对着一个已知答案正确的"参考 agent"（哪怕是手写的固定逻辑）跑一批，统计模拟器自己的违规率，**要求控制在 2%~6% 以内**——超过说明是模拟器的 prompt 有问题，不是被测 agent 的问题，先修这个再往下走

## Step 2 · 建判分引擎（只建 ①③⑤⑥，四种）

| 判分手段 | 谁执行 | 输入 | 输出 |
|---|---|---|---|
| ①终态断言 | 代码 | 检查轮次响应里的 `state` | `state` 是否等于用例的 `期望终态`（VERSION 用） |
| ③禁止动作断言 | 代码 | 全程 `tool_calls` 序列 | 序列里有没有出现 `禁止动作` 列出的调用（一票否决，和其他手段并行跑，不是二选一） |
| ⑤LLM判分 | 判分用 LLM | **只给检查轮次那一轮**的 `assistant_reply` + `tool_calls` + 这条用例专属的 `二元判分问题` | yes/no，和 `期望答案` 比对 |
| ⑥人工抽检 | 人 | 检查轮次范围内的完整对话记录 | 人工给结论（只有 SELFCON 用，按比例抽样，不是每次重跑都要人看） |

**⑤的三条硬约束**（漏一条，不同次判分结果的一致率会从九成掉到四成以下，等于白判）：
- 问题必须窄化成 yes/no
- 必须用这条用例自己的 `二元判分问题`，不能用通用问法
- 只把检查轮次那一轮的内容给判分模型，不要把整段对话都塞进去

### 验收标准

对每种判分器，手工造 2 个假案例——一个"应该判过"、一个"应该判不过"——跑一遍，确认判分器给出的结论和你预期的一致。**这一步在拿到真实 Harness 之前就能做**，用假造的 `tool_calls`/`state`/`assistant_reply` 当输入即可。

## Step 3 · Harness 契约

详细字段定义、请求/响应 schema、联调自查清单见同目录 [`HARNESS_SUT_CONTRACT.md`](HARNESS_SUT_CONTRACT.md)——那份是给 Harness 工程看的，字段不在这里重复。这里只放这一步的**验收标准**：

- Harness 工程照契约接完后，人工连续发 3-4 轮同一个 `session_id`，确认 agent 记得住早轮信息
- `tool_calls` 里的参数是 agent 实际调用的原始值，不是 Harness 转写过的
- 换一个新 `session_id`，状态和记忆确实是全新的，没有残留

---

## Step 4 · 搭 Mock Harness（不用等 Step 3 完成，可以并行做）

**做什么**：按 Step 3 的契约，自己写一个假的 Harness 服务——针对 `CLARIFY-001` 这类场景，手工写死几组"正确回复"和"错误回复"（比如一组严格按条件只问位置不执行，另一组故意提前执行）。

**为什么要做**：Step 1/2/5/6 这四层完全不需要真实 agent 就能测——用 mock 先把"模拟器 → Harness 契约 → 判分引擎 → 统计层"这条链路走通，比等 Harness 工程接完才第一次联调快得多，也能提前暴露你自己这边的 bug。

**验收标准**：用这个 mock 的"正确回复"版本跑，判分引擎应该判过；用"错误回复"版本跑，应该判不过。两个方向都要试，只试一个方向测不出判分器有没有把标准定反。

---

## Step 5 · 重跑与变体执行循环

**做什么**：把"一条用例按 `重跑n` 跑 n 次，每次换一个 `session_id`、选一个轮次变体、独立走完 Step 1→2 全流程、独立记录这一次的 pass/fail"这个循环写出来。n 怎么定见下表（来自源设计文档，不是拍脑袋）：

| n | 用途 | 能报什么 | 不能报什么 |
|---|---|---|---|
| 3 | 冒烟测试 | 通过率、连续3次全对的概率 | 任何分位数 |
| 5 | P1 维度够用 | 通过率、最差一次 | 不要把"最差一次"叫成"10分位"，5个点算不出10分位 |
| 10 | **P0 维度下限** | 上限、波动幅度、10分位（勉强） | 10分位本身仍会抖，别当稳定值汇报 |
| 20+ | 关键维度复核 | 10分位才算真正稳定 | — |

300条P0用例的 `重跑n` 字段本身已经按这个标准填好了（多数是10），不需要你重新决定，照用例里写的跑就行。

**验收标准**：对同一条用例连续跑，能拿到 n 个**互相独立**的 pass/fail 记录（不是跑一次然后复制 n 份），且 session 之间状态互不污染（Step 3 验收过的隔离性在这里应该继续成立）。

---

## Step 6 · 统计汇总层

**做什么**：写卷积代码，不是人工拍：

1. 单例通过率 = n 次里 pass 的比例
2. 50 条用例的通过率 → 这个维度的通过率
3. 6 个维度 → 按分组（记忆与约束/一致性与版本/交互决策）汇总
4. P0 门槛：6 个维度是否都达标，缺一不算清零
5. **正例/负例分开算，绝不合并成一个数字**（比如 CLARIFY 50条里正负例各25，合并会掩盖"该问的时候不问"和"不该问的时候瞎问"这两种完全不同的缺陷）
6. 通过 = 判分手段输出 == 期望答案（注意期望答案不总是 yes，FALSEMEM 就是 no）；叠加多种判分手段的用例，要求全部通过才算这次通过，③是一票否决

**验收标准**：手工构造一批模拟结果（比如故意让 VERSION 全 fail、其他全 pass），跑一遍汇总代码，确认卷出来的分组/P0门槛结论符合你手工算的预期，尤其确认正负例真的是分开报的两个数字，不是被平均掉了。

---

## Step 7 · 小范围联调 → 扩大到 300 条

1. 先只对接 `CLARIFY` 这一个维度（50条），Harness 工程接好后跑一次真实联调，人工核对几条结果是否合理
2. 没问题后依次打开 FALSEMEM / INFERMEM / INSTKEEP / VERSION / SELFCON（SELFCON 最后做，因为多一个人工抽检环节，排期不一样）
3. 全部6个维度打通后，跑一次完整 300 条 P0，产出第一版给主管看的指标

不要一次性把 6 个维度全部接上再联调——出问题时你分不清是哪个维度的判分器错了，还是 Harness 那边哪个字段没接对。
